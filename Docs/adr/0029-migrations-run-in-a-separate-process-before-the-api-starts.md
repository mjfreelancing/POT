# ADR-0029: Migrations run in a separate process before the API starts, in additive steps

**Summary:** In the context of an API that must never serve a schema it does not expect, facing the
choice between applying migrations inside the API and applying them first in their own process, we
decided that a dedicated runner applies migrations and then the API starts, with destructive changes
split into separate additive steps, to achieve a schema that is always current before any request is
served, accepting that a failed migration stops the deployment and that a destructive change takes more
than one release.

## Context and Problem Statement

Two separate problems. First, the process that serves requests must not run against a schema older than
the code that assumes it — the alternative is a class of runtime failures that only happen on a
deployment. Second, a column that is dropped or narrowed cannot be reversed by rolling back the
application binary, so a rolling deployment can have old and new code running against one schema.

## Decision Drivers

- No request should be served by code whose schema is not in place.
- A deployment must fail loudly rather than half-succeed.
- Rolling deployments must not require the old code and the new schema to be incompatible.

## Considered Options

1. A separate migration process that runs before the API, with additive steps for destructive changes.
2. Migrate on application startup, from the API process.
3. Migrations applied by hand before a deployment.
4. One-shot migrations in a deployment pipeline step, outside the image.

## Decision Outcome

Chosen option: 1. The container's entrypoint runs the migration runner to completion and only then starts
the API, so a failed migration stops the container rather than serving a stale schema. The two processes
share an image but are separate executables, so the runner can also be run on its own.

A change that removes or reinterprets existing data is delivered in steps: first a schema that both the
old and new code can use, then the code change, then the removal — each an append-only migration.

Migrations themselves are generated by a person from a reviewed model change. Applying them is not a manual
step: the runner applies whatever has not yet been applied, every time the container starts.

### Consequences

- Good, because the first request a process serves is already against the current schema.
- Good, because a failed migration is a failed container, which is visible, rather than a running API with
  broken queries.
- Good, because additive steps keep old and new code compatible during a rolling deployment.
- Bad, because the entrypoint now owns an ordering the application cannot express, and the platform's
  liveness delay has to allow for migration time.
- Bad, because whether a failed migration stops the container depends on the runner returning a failing
  exit code rather than swallowing the exception.
- Bad, because every replica that starts runs the migration check, so concurrency of migrations depends on
  the runner being safe when it finds the schema already current.

### Confirmation

- Review: a migration that drops or narrows a column in the same release as the code that stops using it
  is a defect; it is split.
- Review: a model change ships with a reviewed migration generated by a person, not applied at startup by
  the API.
- Test: the hosted integration fixture brings its database up to date by running the migrations, so a
  broken or missing migration fails the test run rather than a deployment.

## Pros and Cons of the Options

### Separate runner first (chosen)

- Good: ordering is enforced, and failure is a failed start.
- Bad: another executable and an entrypoint that decides the order.

### Migrate on API startup

- Good: nothing extra to run.
- Bad: the API either serves during migration or refuses to serve while migrating, and both are worse than
  failing to start.

### Migrations by hand

- Good: full control of timing.
- Bad: depends on a person remembering, and leaves no record that a deployment ran them.

### Pipeline step

- Good: cleanest separation, and easy to gate.
- Bad: there is no pipeline; deployment is a local task, so this would be a step that does not exist.

## More Information

- Deployment without a pipeline is a separate decision.
- The readiness signal that reports the schema is migrated belongs to the health-probe work.
