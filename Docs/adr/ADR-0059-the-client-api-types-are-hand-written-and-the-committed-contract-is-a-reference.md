# ADR-0059: The client's API types are hand-written, and the committed contract is a reference

**Summary:** In the context of a client whose API types are Zod schemas used only to derive TypeScript
types, facing a committed OpenAPI document that could generate them, we decided to keep the types written
by hand and treat the contract as a reference, to achieve types shaped for the client's own use without a
codegen toolchain in the build, accepting that a contract change is not a compile error and that drift is
found at runtime.

## Context and Problem Statement

The API contract is generated by the server build and committed (`contracts/openapi/v1.json`, ADR-0049), so
a machine-readable description of every operation exists in the repository. The client does not use it as a
build input: `Source/Client/pot-react/package.json` has no generator, and its types are Zod schemas in
`src/data/*.ts` that exist for `z.infer`. Nothing in `src/` calls `.parse` or `.safeParse` on API data — the
count is zero — and responses arrive as `JSON.parse(text) as unknown` and are then cast
(`src/api/apiHelpers.ts:88`).

That makes the contract a reference rather than a source, and the trade-off is visible. The Etag schema
declared `z.bigint()` while the hand-written API type declared `number`, and nothing compared them, so the
mismatch shipped. Reading the contract is also not straightforward: numbers are published as
`["number","string"]` with a pattern, because the server accepts numeric strings when reading, so a
generator applied without a schema change would make every numeric field on the client a union.

Timing matters for the date: the decision became consequential on 2026-10-19, when the contract started
being generated and committed. Before that there was nothing machine-readable to generate from, so the
client's types could not have been anything but hand-written.

## Decision Drivers

- The client's types serve more than response reading: they shape forms, results and component props.
- There is no continuous integration (ADR-0031), so a "generated file is current" check would be a manual
  step that drifts like the contract does.
- A codegen step becomes part of every client change, and its output has to be reviewed.

## Considered Options

1. Hand-written types, with the committed contract as a reference (status quo).
2. Generate the response types from the contract.
3. Keep the hand-written types but validate responses at runtime with the existing schemas.

## Decision Outcome

Chosen option: 1, because the client's types are not a transcription of the contract — they carry the
shapes the client works in — and because a generator's output is only trustworthy if something checks it
is current, which needs CI this repository does not have.

The rules it imposes:

- The committed contract is the reference for a response's shape. The client's types are written to match
  it, never generated from it.
- A schema in `src/data/*.ts` exists to give a TypeScript type. It is not a runtime validator, and adding
  `.parse` or `.safeParse` to an API response path is a change to this decision, not a local improvement.
- When the contract and the client disagree about a field's type, the contract wins and the client is
  corrected.
- Adding a field to the contract needs no client change. Renaming or retyping one does, and nothing will
  fail until the code that reads it runs.

### Consequences

- Good, because there is no generator, no generated file to keep current and no dependency on CI.
- Good, because the client's types can express client-only shapes — results, failures, form models —
  without being bent into the contract's vocabulary.
- Good, because the contract stays documentation that a person reads rather than a build input.
- Bad, because a contract change is not a compile error on the client, and the Etag mismatch shows that
  drift of this kind can ship unnoticed.
- Bad, because nothing compares the two, so the guard is a reviewer who reads the regenerated contract.
- Bad, because runtime validation is not available while this record stands, so a malformed response is
  still trusted once cast.

### Confirmation

- Package: `Source/Client/pot-react/package.json` carries no OpenAPI generator; adding one is a change to
  this decision.
- Code: no `.parse` or `.safeParse` on API data in `src/`, and responses are cast from `unknown` in
  `src/api/apiHelpers.ts`.
- Review: a generated types file, or a parse added to a response path, is a change to this decision rather
  than a refactor.

## More Information

- Option 2 would first need a server-side schema transformer so numbers publish as `number`; otherwise
  every generated numeric field is a union. It would also need the currency check that PRD-0034 would
  provide, which is why it was not taken now.
- Option 3 (runtime validation) is available on its own: the schemas already exist and Zod objects are
  non-strict, so a new server field is tolerated while a renamed one would fail. It was not taken because
  the validation would be a behaviour change in the client's request path rather than a type decision.
- The Etag type this record cites is corrected as a client-only change; the concurrency question it came
  from is ADR-0001's, and that record stands.
