# Dynamic Accrual Calculation PRD

**Status:** Complete
**Priority:** Medium
**Last Updated:** 2026-09-29
**Feature ID:** 023
**Scope:** Replace persisted expense-accrual state with on-demand calculation. One accrual engine becomes the single authority for `TotalExpenseAccrued`, `DailyExpenseAccrual`, `StableExpenseAccrual` and per-expense `Accrued`, evaluated for an as-of date whenever values are read (`/accounts`, `/expenses`, `/projections`). Covers the server read paths, the removal of the accrual command surface and dirty/status machinery, the client surfaces that consume it (dashboard cards and overview, accounts table, expenses `Accrued` column, accrual quick actions and status context), the append-only migration path that drops the persisted columns, and the maintenance import/export implications. `NextDue`, renewal semantics and the overdue rule are unchanged; the projection engine's outputs change only where an occurrence's settlement state is mis-measured today (§3.1) and by the schedule-derived `Arrears` term for cycles already past due (§3.2). The calculation is expressed over explicit input and output models so that no entity is mutated and no derived value can be persisted.
**Audience:** Future implementation agent(s), reviewers, and maintainers.

## Purpose

Make expense accrual a pure function of `(expenses, asOfDate)` evaluated at read time, so there is no stale accrual state to refresh, no dirty-flag or last-accrued bookkeeping, no manual "accrue" step, and exactly one derivation of "available" across the dashboard, accounts table, expenses list and projections.

## Scope

### In Scope

- Refactoring `AccrueExpenseCalculator` into a pure calculation over explicit input models that returns an immutable accrual view, so no entity is mutated and no derived value can reach the database. It is now `AccrualCalculator`, with `IAccrualCalculator` as its interface; §4 names it as it was, because that section describes the code being replaced.
- Introducing the models that feed and return it: an immutable per-expense input record, an immutable per-account view, and the repository projection that produces the input without materialising expense graphs.
- Moving the accrual arithmetic that lives in `Pot.Data/Extensions/ExpenseEntityExtensions.cs` into the calculation, so all accrual maths has one home.
- Server read paths: `GET /api/accounts`, `GET /api/accounts/{id}`, `GET /api/expenses` and `GET /api/projections` all obtaining accrual values from that one engine for the same as-of date.
- Removal of the accrual command surface: `POST /api/accruals/accrue-expenses`, `AccrueExpensesService`, `AccrualDirtyStateManager`'s dirty/clean responsibilities, the accrual half of `/api/accruals/status`, and the accrual-relevant account accrual storage.
- Client removal: the "Accrue Expenses" quick action, the combined "Renew & Accrue" action (removed entirely, since the two separate renew actions already cover everything that would remain) and the accounts table's bulk "Accrue Expenses" action, plus the accrual status context state and its refresh triggers. The `features/dashboard/actions/accruals` barrel drops its removed exports with them, and the Quick Actions grid keeps its four desktop columns (§4, §8).
- Client addition: the arrears figures the read paths now return are carried in the client schemas and shown on the accounts table and the expenses list (§8).
- Schema changes via new, append-only EF migrations (the existing `AddAccountAccrual` / `BackfillAccountAccrual` migrations are not touched).
- Maintenance import/export handling for the affected columns.
- The projection accrual basis for un-settled occurrences (§3.1) and the schedule-derived `Arrears` for cycles already past due (§3.2), including the deliberate change to payment-day and overdue `Available` values.
- Documentation updates to match the changed behaviour: `Docs/ARCHITECTURE.md` (the dual-metric accrual description), `Docs/FEATURES.md` (the Quick Actions summary's "accrue account expenses" line and the "Expense Accruals" entry), `Docs/USER-GUIDE/` (`Accounts.md`, `Dashboard.md`, `Projections.md`, and `_DOCUMENTATION_PLAN.md` — its "Accruing Account Expenses" section and its "accrue expenses before…" guidance, not only the available-calculation section), plus `Source/Server/IMPLEMENTATION.md` and `Source/Server/DEVELOPER.md` (both carry the stable/dynamic accrual semantics referenced by PRD-003; the developer guide also reproduces the `AccountAccrual` model configuration, site query filter and data-layer file listings).

### Out of Scope

- `NextDue` semantics. It remains the user-entered value from create/edit, advanced only by renewal, and remains the single source of "overdue" (`NextDue < today`).
- Renewal behaviour and `RenewalMode.Overdue`/`Future` semantics, and the renewal half of `/api/accruals/status`. Renewal's _implementation_ does become a pure calculation so the projection loop carries no mutable simulation state, but that is an internal change decided under the model design in §1 (OD-08); the behaviour it produces for the user is unchanged.
- The projection engine's calculation rules, forecasting window, or metric set.
- A settlement/actuals ledger. That is a separate, independent track — see [PRD-024](PRD-024-settlement-ledger.md).
- Site locale/currency (PRD-018) and deletion flows (PRD-022), beyond noting the interactions recorded below.

## Problem Statement

Expense accrual results are persisted, so they are stale the moment anything they depend on changes — and they depend on two different clocks.

| Clock    | Trigger                                                                                                  | Effect on persisted accrual                                     |
| -------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Event    | Expense create / accrual-impacting update / reassignment / exclusion toggle / renewal / impactful delete | The account's accrual aggregate no longer reflects its expenses |
| Calendar | A local day boundary passes                                                                              | The daily accrual ramp moves on regardless of any user action   |

The calendar clock is the binding one: an account's status goes stale **every day with no edits at all**, which is why the dashboard carries a permanent "accruals are pending" state and a manual "Accrue Expenses" quick action. An edit-time hook cannot remove that step; only deriving the values (or automating the trigger) can.

Persisting a derived value also brings its own costs:

1. **Write amplification and etag churn.** An accrual pass rewrites every expense whose `Accrued` changed, plus the account row and the account accrual row. `DbContextBase.OnBeforeSave` stamps a fresh `Etag` on each `Added`/`Modified` entry, so a "refresh" of derived data invalidates concurrency tokens on unrelated rows. PRD-009 explicitly designed around this churn.
2. **Two answers to one question, on two different bases.** `Available = Balance - Reserved - TotalExpenseAccrued` is exposed from `/accounts`, while `ProjectionsService` computes `Available = balance - reserved - accrued + expensesPaid`. Beyond staleness, the two measure different things: `/accounts` accrues a full obligation for an occurrence that is due or overdue and not yet acknowledged, while the projection advances the schedule before measuring and therefore reports the next cycle's partial accrual instead. The disagreement is structural, not merely temporal, and it is widest exactly when the obligation matters most.
3. **Duplicate implementation of the same rules.** The accrual rules (policy modes, accrual-start handling, one-time boundaries, stable vs daily contribution) live in one calculator, but the _decision of when they are applied and whether the result is current_ is spread across the dormant dirty-state manager, the status specification, the command service and the client's refresh triggers.
4. **Invalidation machinery with failure modes.** Every mechanism proposed to keep the persisted value fresh — accrue on each mutation, accrue at login, accrue on a schedule, write-during-GET — is an invalidation strategy for a value the application can already compute. Each adds a trigger, and the scheduled/login variants add a new failure domain (missed window, duplicate execution per replica, auth-path coupling) for a result that is idempotent per `(account, asOfDate)`.

### Identified defect: the projection loop measures after advancing the schedule

`Source/Server/IMPLEMENTATION.md` documents the accrual rules: on the due date `Accrued` is set to the full `Amount` regardless of elapsed days, and a recurring expense then begins accruing for the next period from that date. `MapToDateBalanceAvailable` depends on the first rule — it adds `ExpensesPaid` back "because the accrued amount already considers the expense total".

`ProjectionsService` breaks that combination for any item due today or already overdue, because it calls `Renew(Overdue, date)` **before** `AccrueExpenses(...)`. Renewal advances `NextDue` past the measurement date, so the accrual takes the next period's branch and reports a partial amount — zero on the day the item is due — instead of the full amount the add-back assumes. For a 1000 balance and a 100 monthly bill due today:

| Measurement                                     | `Accrued` at the read date                            | `Balance` | `Available` |
| ----------------------------------------------- | ----------------------------------------------------- | --------- | ----------- |
| Projection (current)                            | 0.00 — next period, zero days elapsed                 | 900       | **1000**    |
| Documented rule, and the dashboard accrual path | 100.00 — full amount for the occurrence being settled | 900       | **900**     |

The visible consequence is that `Available` exceeds `Balance` on every payment day by the total of that day's accruing bills, which also masks a temporary overdraft on the day it exists; the figure corrects itself the next day, so it presents as a one-day spike rather than a persistent error. The same ordering understates an un-settled overdue occurrence for the same reason (§3.1). Two assertions encode the current result — `"accrued(0, just reset) + expensesPaid(900) = 5000"` and `"accrued(0, just reset) + expensesPaid(200) = 4000"` — so no test currently flags it.

Two further defects come from the same ordering and need more than the settlement-basis fix: the overshoot also survives for any due row that does not accrue (`AccrualPolicy.None`, or a null `AccrualStart`), because `expensesPaid` is built without a policy filter while `Accrued` excludes it; and an un-settled _overdue_ row has no correct basis at all under a single-cycle accrual rule, so the design carries its obligation as `Arrears` instead (§3.2). Both are settled in the Decisions section and quantified in `## Behaviour Changes`.

The projection engine demonstrates the alternative: `ProjectionsService` renews overdue items and accrues each day of the forecast **in memory, without persisting anything**, for every account and every day in the window. It never reads the persisted accrual columns. The persisted values therefore exist only to serve the non-projection surfaces, and are a stale copy of what those surfaces could compute.

## Proposed Design

### 1. One calculation over explicit models, evaluated on read

#### 1.1 Input and output models

The calculation takes an explicit input model instead of entities, and returns an immutable view instead of writing into them (shapes indicative; naming to be settled in implementation):

```text
ExpenseAccrualInput                       // immutable record, one per expense
  RowId                                   // identity, so per-expense results can be attributed
  ExcludeFromCalcs
  AccrualStart, NextDue, EndDate
  AccrualPolicy, Frequency, FrequencyCount, Amount

ExpenseAccrualPosition                    // the facts paired with the schedule cursor they are measured against
  Facts: ExpenseAccrualInput, Cursor: AccrualCursor (NextDue, AccrualStart)

AccountAccrualView                        // immutable record, one per account
  TotalExpenseAccrued                     // Σ Accrued — the cycles in progress; meaning unchanged
  TotalArrears                            // Σ Arrears — the cycles already past due (§3.2)
  TotalCommitted                          // TotalExpenseAccrued + TotalArrears — headline obligation
  DailyExpenseAccrual
  StableExpenseAccrual
  Expenses: [ { RowId, Accrued, Arrears } ]        // detail shape only; see 1.4
```

All of these are produced: the three aggregate metrics, the new `TotalArrears` / `TotalCommitted`, and per-expense `Accrued` / `Arrears` for `/accounts` and `/expenses`. **Amended after implementation (2026-09-27):** the account's identity was removed from both models, and the `accountId` parameter from both `IAccrualCalculator` entry points. The original shapes carried `AccountId` on the view and on the input for what §1.4 called explicit attribution, but every caller supplies the positions for one account it already holds, so no production code read it — it was write-only state echoed back to its own caller, and the audit that caught it (every retained field must back a reader) decided to delete it rather than carry it. `DailyExpenseAccrual` still feeds the projection response's `dailyAccrual` metric and its chart series; only the accounts response stops exposing the daily field (§8), so do not remove the metric from the calculation. `ExpenseAccrualInput` needs no new field for arrears: the count of past-due occurrences is derived from `NextDue`, `Frequency`, `FrequencyCount`, `EndDate` and `Amount` against the as-of date, by walking the schedule forward from the persisted `NextDue` and counting each occurrence strictly before that date (§3.2).

**Amended after implementation (2026-09-27) — the headline aggregate renamed.** `TotalOutstanding` is now `TotalCommitted` (`totalCommitted` on the wire) and the accounts column is labelled `Committed`. "Outstanding" is a settled-debt term — money due and unpaid — so it described the `Arrears` component accurately and the accrual of the cycle in progress inaccurately: that accrual is not owed yet, which is the same distinction §3.2 draws when it refuses to fold arrears into `Accrued`. "Committed" holds both halves without over-claiming either, and it matches the participle form of the labels beside it. The figure, its derivation and its use are unchanged — still `TotalExpenseAccrued + TotalArrears`, still what `Available` subtracts (§3.2). The rename is carried through `AccountAccrualView`, the calculator, both accounts `Output`s and `EntityMapping`s, both `Response`s (field name and OpenAPI description), both test projects and the client schema, so no layer keeps the old term; the label drops the `Total` prefix for the reason §8 gives.

`Pot.App/Concerns/Accruals/Models/ExpenseAccrualState.cs` already carries every input field except `RowId`, and its current purpose — the before/after comparison used to mark accounts dirty — is removed by this feature. It is therefore **repurposed and renamed** (`ExpenseAccrualInput`), with `RowId` added, rather than replaced by a new type.

`AccountEntity` leaves the calculation signature entirely. The calculator currently both reads and writes it; the three account aggregates become results, and `Balance`/`Reserved` stay in the mapping layer where `Available` is composed.

The existence of `AccountWithLinkedCounts` (`Pot.Data/Repositories/Accounts/Dtos`) establishes that narrow, EF-projectable read models are an accepted pattern here. Whichever placement is chosen, the repository must project only the fields listed in 1.1 rather than materialising expense graphs.

#### 1.4 Two shapes, one implementation

`/expenses` needs `Accrued` and `Arrears` per row; `/accounts` and `/projections` need only the account totals. A per-expense collection allocated per account per day would be pure waste in the projection loop, so the calculation exposes two entry points over one private implementation:

```text
CalculateAccountTotals(inputs, asOfDate)             -> account totals only: the three accrual metrics
                                                        plus TotalArrears and TotalCommitted
CalculateAccountWithExpenseDetail(inputs, asOfDate)  -> the same totals plus per-expense Accrued and Arrears
```

`inputs` is a read-only collection of `ExpenseAccrualInput` for **one** account. Neither the input nor the returned `AccountAccrualView` carries the account's identity: a caller supplies the positions for a single account, so it already knows which account the view describes, and the per-row results are attributed by `RowId`. The accounts read path passes the single account it is projecting; the expenses read path groups its rows per account and attributes each per-row result by `RowId`.

The detail shape covers **every** row of the requested account — including excluded rows, `AccrualPolicy.None` rows and rows with a null `AccrualStart` — each contributing `Accrued = 0` where nothing accrues and `Arrears = 0` where no occurrence is past due. The expenses list renders a value for every row, so a shape that omitted rows would leave its own column unexplained, and it returns `Arrears` alongside `Accrued` so the past-due portion is shown separately from the cycle in progress (§3.2). This is the **expense-read** contract specifically: the two expense endpoints load every row of the account, whereas the accounts and projection queries exclude rows in their own query (§1.6).

The detail shape is the contract of the two expense read endpoints (`GET /api/expenses`, `GET /api/expenses/{id}`), which expose per-row `Accrued` and `Arrears` for the expenses table's columns (OD-07). It is deliberately **not** produced for the projection window: per-item accrued across every day of the window would multiply the detail allocation by the window length for a figure nothing renders today. The projection loop is the one place the detail shape is _produced without being emitted_: on a day whose paid set is non-empty it calls the detail entry point and uses those rows' `Accrued` for the payment-settled accrual add-back (§2), reading the aggregates from the same call; on every other day it calls the totals entry point, so no per-expense detail is allocated on a day nothing reads it. If a projection surface ever needs per-row accrual for display, it is computed **on demand for the single date that surface is showing**, not across the series.

#### 1.5 The projection loop

The loop is the one place where the input strategy carries a cost, because the schedule moves as it walks days: it currently renews _and_ accrues by mutating the same objects, 365 times. The load-bearing detail is _when within a day_ the schedule is read: the due check and the paid set measure the cursor at the start of the day, the accrual is always taken for the **cycle in progress** (defined in §3.2 as the first occurrence at or after the as-of date), and only then is that day's renewal folded in. Reading the already-advanced state is what produced the defect in the Problem Statement.

| Option                                    | Mechanism                                                                                                                                                                            | Assessment                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1. Per-day immutable snapshot            | Re-read (and re-project) the measurement input on each forecast day instead of holding it fixed                                                                                      | Simple contract, 365 × M mappings, and an ordering hazard that only tests catch                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| P2. Read-only contract over mutable state | Simulation objects implement a get-only `IExpenseAccrualInput`; renewal mutates them, the calculation can only read                                                                  | No snapshots, no allocation, and the type system enforces read-only inputs. Rejected anyway: the settled semantics need the start-of-day cursor for measurement while renewal advances the same state, so a get-only view of live mutable objects cannot express both readings within one day without an ordering contract the type system does not enforce                                                                                                                                                                                                       |
| P3. Pure renewal plus a value-type cursor | Immutable facts per expense plus a small `readonly record struct` cursor (`NextDue`, `AccrualStart`); renewal folds the cursor and the calculation takes `(facts, cursor, asOfDate)` | **Settled** (OD-08). No mutation of the accrual facts anywhere in the loop — and the running balance becomes loop-local, so no entity is written either — no meaningful allocation (a two-date value type), the ordering hazard disappears because the cursor is derived rather than read, and renewal becomes as testable as accrual. Requires pure counterparts for `ExpenseRenewalCalculator`/`IncomeRenewalCalculator`; the renewal _command_ path still writes the computed cursor back to the entity, because a schedule advance is a fact worth persisting |

Under P3 the loop carries **one** cursor per expense: a value seeded from the persisted schedule and folded forward as the loop walks days. There is no second, parallel cursor — the distinction the design needs is _when_ within a day the cursor is read, not two pieces of state.

**The ordering is per day, not read-date-only — and the accrual is always of the cycle in progress.** Each day fully resolves a row's state against the cursor value **at the start of that day**, then folds that day's renewal: the due check and the paid set use the start-of-day `NextDue`, while the accrual is measured for the cycle in progress. A **strictly past-due** occurrence therefore contributes `Arrears` and never accrual, so such a row accrues its next cycle's ramp — this is what stops the preserved `currentDate < NextDue ? ramp : Amount` rule from accruing the past-due occurrence in full and reporting the interim `0` that §B-06 records as superseded. On the read date the start-of-day value is the persisted one, which is why an un-acknowledged occurrence is counted in full instead of being released by the loop's own catch-up (OD-01) — as the current bill's `Accrued` when it is due today, and as its `Arrears` when it is already past due (§3.2) — while on every later day the start-of-day value is the already-folded one, so the assumed payment has been made and the occurrence is released rather than counted a second time (OD-11). Measuring _after_ the advance — today's order — reproduces the defect on **every** payment day of the window, not only day 0: a recurring bill due on day 31 overshoots exactly as one due on day 0 does, because both reset the same way before being measured (OD-15).

**The running balance is loop-local.** The loop must not write `AccountEntity.Balance`/`Reserved`; it carries a per-account accumulator seeded from the account row. Today's loop breaks this (`account.Balance += …` inside the day loop), protected only by the projection request never calling `SaveAsync` — which is the same "merely unintended, not impossible" argument §1.2 rejects for the accrual facts, so the balance is held to it too.

Because the accrual basis changes for un-settled occurrences and the arrears term is added, projection outputs are **not** byte-for-byte identical to today's. The deliberate differences are exactly those enumerated in `## Behaviour Changes` — the payment-day overshoot (B-01, B-03), the past-due obligation carried as `Arrears` (B-02, B-10), and the response and export shape changes (B-08, B-09) — and the projection fixtures are updated to match (see Tests and Validation). Any other difference is a defect in the refactor. In particular, the read-date `DailyAccrual` of a past-due row is **unchanged** (B-06).

The read date is **always site-local today** (`ITimeProvider.GetLocalDateNow()`), even when `options.StartDate` is later. `GetPreStartDays` already simulates the days between today and the requested start so the balance is carried forward correctly; those days are consumed internally and never emitted. An un-acknowledged occurrence is therefore measured against the persisted cursor on today and, for the **current cycle**, released from the next day, so a window that starts in the future contains no un-settled _current-cycle_ obligation — by design, because its whole span sits under the on-time-payment assumption. `Arrears` is the exception: it is pre-existing debt computed once at the read date and held for the whole window (§3.2), so a future-start window still carries it on every emitted day. The un-acknowledged obligation stays visible where its own basis applies: the accounts page, the account cards and the expenses list, all of which read today.

#### 1.6 Rules preserved

The existing rules are preserved exactly: `AccrualPolicy.None` short-circuits, `AccrualStart` gating, the one-time due-date boundary, the stable-metric fixed-denominator rule for one-time items and the end-date gate for recurring items, and the "due today is fully accrued but not paid" treatment. The as-of date comes from `ITimeProvider.GetLocalDateNow()`. The calculation is the only place accrual arithmetic lives, and it is shared by every consumer.

A null `AccrualStart` is not an accrual start of zero: it keeps today's rule, where the row is not processed and contributes `0` to the aggregates and to its own `Accrued`. The branch is **defensive** — create and update canonicalise the value through `AccrualPolicyExtensions.GetCanonicalAccrualStart`, which returns the caller's default when `AccrualPolicy.Automatic` has no explicit start, so a null start is reachable only through import or legacy data. `AccrualPolicy.None` is the user-reachable configuration of the same shape and is documented as such (`Docs/ARCHITECTURE.md`), so it is the case the projection's basis must handle deliberately (OD-15). Exclusion is decided once, by the repository query: the accounts and projection queries do not load excluded rows at all, while the expense reads do, because the list renders a value per row (§1.4). The calculation keeps its `ExcludeFromCalcs` guard as a documented invariant — so the function is correct on its own terms — rather than as a second, competing decision point. `Arrears` is the one rule that does **not** follow `AccrualPolicy` or `AccrualStart`: it is derived from the schedule (occurrences already past due), so a `None` or null-`AccrualStart` row can still carry arrears (§3.2). Exclusion still decides whether the row is loaded at all.

### 2. Read paths consume the view

| Path                                          | Change                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/accounts`, `GET /api/accounts/{id}` | The repository projects the accrual-relevant expense fields into the input record (§1.3) and the calculation produces the aggregates plus `TotalArrears`; the existing output members are populated from them. `Available = Balance − Reserved − TotalExpenseAccrued − TotalArrears` (§3.2)                                              |
| `GET /api/expenses`                           | Populate the per-row `Accrued` and `Arrears` from the detail shape (§1.4) for the same as-of date                                                                                                                                                                                                                                        |
| `GET /api/projections`                        | Adopt the model in §1.5, call the same calculation on the start-of-day cursor, and hold `Arrears` for the whole window (§3.2, OD-17). Outputs change where settlement state was previously mis-measured (§3.1, OD-15) and by the arrears term (§3.2, OD-17); the fixtures are updated deliberately to guard against any other difference |

**`Available`, defined once.** The accounts read uses `Balance − Reserved − TotalExpenseAccrued − TotalArrears`, composed from `TotalCommitted` (§3.2) so the headline obligation is derived once; the projection chart uses `balance − reserved − accrued − arrears + expensesPaid`, where `balance` is the running forecast balance and the add-back is the payment-settled accrual. These two forms are the single authority for this document — every other section references them rather than restating them — and the chart's payment-settled accrual is qualified immediately below.

What is now shared across the read paths is the accrual basis, not the balance: the chart still applies its own assumed payments inside the window, so its `Balance` — and therefore `Available` — can differ from the card's user-maintained balance. Neither `Balance` nor `Reserved` is an accrual input: both stay where the account response is composed. Response shapes change in exactly two ways: the accounts response stops exposing `dailyExpenseAccrual` (OD-06, §8), and the accrual-bearing reads gain the arrears figures — `totalArrears` / `totalCommitted` on the account responses and a per-row `arrears` on the two expense reads (§3.2, OD-17). No other read response and no write payload changes shape.

The chart's `Available` add-back needs one qualification. Its formula is `balance - reserved - accrued - arrears + expensesPaid`, and re-adding `expensesPaid` is only correct where the rows it contains already contribute their full amount to `accrued` — otherwise the day is credited for an obligation it never accrued. That holds for every accruing row measured at the start of its due day, and fails for the non-accruing case described in the Problem Statement. The add-back is therefore the **payment-settled accrual** rather than a blanket sum (§B-03). A past-due occurrence is not counted as paid at all — it is carried as `Arrears` and held for the window (§3.2, OD-17), which supersedes OD-15 option (a)'s overdue debit and removes the day-1 discontinuity that debit existed to fix (§B-04). `Arrears` is a separate subtraction on the same `Available` line and is **not** part of the add-back: it is a standing obligation, not a payment.

### 3. `NextDue` and renewal do not change

`NextDue` stays exactly what it is today: the value the user enters on create/edit, advanced only by renewal, and the sole basis for "overdue" (`NextDue < today`). Renewal behaviour is unaffected; whether its implementation also becomes a pure calculation is settled in §1.5 (OD-08). The renewal-derived signals that depend on `NextDue` — overdue/due-today/due-soon/ended badges, dashboard overview windows, the bulk renew confirmation breakdown, and `BudgetReminderService` — all continue to behave as they do now, because nothing in this feature moves the cursor.

#### 3.1 Worked examples: the same bill in four settlement states

The examples use the same inputs throughout: account `Balance = 1000`, `Reserved = 0`, no incomes, and one expense of 100 with `Frequency.Months` and `AccrualPolicy.Automatic` on a 31-day cycle. The read date is day 0, and `Available` is defined in §2 — for these fixtures the accounts and chart forms agree, so each row is stated as `Accrued` + `Arrears` → `Available`.

"Settled" means the user has renewed (marked the occurrence paid); it is the only settlement record the product has today, so these four states are distinguished by the cursor, not by the movement of money.

| Settlement state on the read date     | Cursor (`NextDue`, `AccrualStart`)     | Counted as paid in the window | Today: `Accrued` → `Available` | This feature: `Accrued` + `Arrears` → `Available` |
| ------------------------------------- | -------------------------------------- | ----------------------------- | ------------------------------ | ------------------------------------------------- |
| Paid a day early — settled on day −1  | `day 31`, `day −1`                     | none                          | 3.13 → **996.87**              | 3.13 + 0 → **996.87**                             |
| Paid on the day — settled on day 0    | `day 31`, `day 0`                      | none                          | 0.00 → **1000.00**             | 0.00 + 0 → **1000.00**                            |
| Not yet paid, still due today         | `day 0` (accrual start not used)       | 100, assumed by the window    | 0.00 → **1000.00**             | 100.00 + 0 → **900.00**                           |
| Paid a day late, not yet acknowledged | `day −1`, then `day −1` after catch-up | none                          | 3.23 → **996.77**              | 3.23 + 100.00 → **896.77**                        |

Rows 1–2 are settled, so nothing changes for them. Row 3 is the payment-day defect: today the row is measured after the schedule is advanced, so `Accrued` is the next period's ramp (`0.00`) and the add-back credits the day for a payment that was never accrued — `Available` reads `1000.00` while `Balance` is `900`. Measuring at the start of the day makes `Accrued` the full `100.00`, so the add-back cancels it and `Available` reads `900.00`. Row 4 is the arrears change: the past-due occurrence is carried as `Arrears` (`100.00`) while the cycle in progress contributes its ramp (`3.23`), so `Available` falls to `896.77`; today the same obligation appears only in `Accrued` and `Available` reads `996.77`. These four rows are the arithmetic authority for the rest of this document.

1. **The settled states are unaffected.** When the cursor has already been advanced there is nothing to catch up, so today's code and this feature agree: `Available` is the balance less the accrual ramping towards the next occurrence.
2. **The un-settled states are the defect in numbers.** Today the chart barely distinguishes settled from un-settled — 0.00 or 3.23 of accrual where the obligation is the full 100 — which is why clearing a bill appears to change so little.
3. **"Paid late" and "not paid at all" are the same input.** With no payment record the product cannot tell them apart, so both hold the same obligation until the user acknowledges one of them. This is the gap PRD-024 exists to close.
4. **One obligation per missed cycle, carried as arrears (supersedes the original one-`Amount` rule).** The obligation is one `Amount` for each past-due, un-settled occurrence, accumulated as `Arrears` (§3.2, OD-17) rather than folded into `Accrued`. POT still forecasts forward on the basis that income is received and expenses are paid on time, but it now also reflects how far behind the account already is: arrears has a real effect on `Available`, so it is counted. The accrual _rule_ is unchanged — the cycle in progress still accrues only up to its own `Amount`.
5. **Day 1 and beyond, and what "released" means for each row.** The **due-today** row's obligation is held on the read date only (OD-11, settled): its balance has already lost the payment — `IsDueOnDate` matches, so it is counted in `expensesPaid` — and holding the obligation any longer would subtract it a second time, because the accrual would keep taking it against a balance that already paid it. The **overdue** row is no longer released: its obligation is carried as `Arrears` and held for the whole window (§3.2), so there is no day-1 jump and no balancing debit to invent. OD-15 option (a)'s overdue debit is therefore superseded for rows carried in arrears (§B-04). The read date is today even when the requested window starts later, so a future-start window still shows no _current-cycle_ un-settled obligation; its arrears, being pre-existing debt, is held throughout (§1.5, §3.2).
6. **The accrual columns stop being stale and agree with the chart.** The accounts page's "Total Accrued", the accounts "Daily Need" and the expenses list's `Accrued` currently hold whatever the last manual accrual computed, so they can be a day behind or miss an edit entirely, while the chart independently computed its own, different value. After the change one calculation feeds all three, so an un-settled obligation reads in full everywhere — as `Accrued` for a bill due today, and as `Arrears` for past-due cycles (§3.2). The existing columns keep their meaning; what changes is that they are current and consistent, with the arrears figures alongside them (§3.2). The columns' values change only through the corrections above (OD-07, §8, §B-05).
7. **`dailyAccrual` and the overdue row.** With the obligation for a past-due occurrence carried by `Arrears` rather than `Accrued` (§3.2), the overdue row's `Accrued` is the cycle in progress, so `DailyExpenseAccrual` reports that cycle's ramp (≈`3.23`) rather than the `0` a fully-accrued obligation would leave behind. The two rows reach the same rate by different expressions — `DailyBalance` gives `(100 − 3.23) / 30` on the overdue row, `Amount / daysToNextDue` gives `100 / 31` on the due-today row — so they agree to two decimals for this fixture without being the same expression, and they need not agree in general. This supersedes the `0` interim recorded in §B-06; the read-date rate is unchanged from today's.

#### 3.2 Arrears: the obligation for cycles already past due

§3.1 note 4 originally settled that an un-settled item represents **one** obligation. This feature changes that: an item the schedule has fallen behind on carries **arrears** for every occurrence whose due date is already past and that the user has not settled. The accrual rule itself is unchanged — a cycle still accrues only up to its own `Amount`, and the cycle in progress still ramps and stops at its total — so the change is additive rather than a redefinition of accrual.

**Terminology (settled).** Three amounts are kept distinct:

| Term             | Meaning                                                                 | Worked example below |
| ---------------- | ----------------------------------------------------------------------- | -------------------- |
| `Accrued`        | the accrual of the cycle currently in progress, bounded by its `Amount` | `30.00`              |
| `Arrears`        | `Amount × past-due, un-settled occurrences`                             | `140.00`             |
| `TotalCommitted` | `Accrued + Arrears` — the headline obligation                           | `170.00`             |

`Accrued` keeps its current meaning and its bound, so the daily/stable rate metrics and the `Amount − Accrued` arithmetic remain valid; `Arrears` is the new, separately-named past-due component; `TotalCommitted` is what the UI shows when it wants one number. It would be wrong to call the past-due amount "accrued": it is not accrual, it is debt, and naming it `Arrears` is what lets the accounts page and the expenses list show it as such, and the projection reflect it through `Available`.

**Worked example.** A $70 weekly bill accruing $10/day, two cycles missed and three days into the third:

- occurrences due on day 0 and day 7 have passed and are un-settled → `Arrears = 2 × 70 = 140`
- the cycle in progress is due on day 14 and is 3 days in → `Accrued = 3 × 10 = 30`
- `TotalCommitted = 170`, and `Available` falls by `TotalCommitted`

**Rules:**

- Starting from the persisted `NextDue`, walk the schedule forward by `Frequency` / `FrequencyCount`: every occurrence whose due date is **strictly before** the as-of date contributes one `Amount` to `Arrears`, and the first occurrence at or after the as-of date is the cycle in progress. The count is therefore computable from the persisted schedule alone; it is computed once at the read date and then held for the window (see the window rule below).
- An occurrence is arrears when its due date is **strictly before** the as-of date. A bill **due today** is the current bill: it accrues in full (`Accrued`), is assumed paid in the forecast, and is **not** arrears. This boundary is what stops a due-today bill being counted twice.
- Arrears follows the **schedule**, not the accrual policy: a past-due occurrence contributes to arrears even when `AccrualPolicy.None` or `AccrualStart` is null, because being behind on a bill is not the same question as whether the bill accrues. `ExcludeFromCalcs` remains the opt-out — excluded rows are not loaded by the accounts or projection queries at all (§1.6).
- Arrears stops at `EndDate`: occurrences beyond the end date are not counted, and a one-time item (which does not renew) carries at most the one occurrence.
- Arrears uses the **current** `Amount` for every past-due occurrence. An amount change therefore reprices history; correcting that needs the captured amount snapshot in [PRD-024](PRD-024-settlement-ledger.md), which is a history record and must not be read by this calculation.

**Projection window (settled): arrears is held for the whole forecast.** The forecast assumes every occurrence _from today onward_ is paid on time; arrears is the debt that already exists _before_ the window opens. It is therefore subtracted from `Available` on **every** day of the window and is not released, and it is not debited from the forecast `Balance` — the arrears is not assumed to be repaid inside the window. This differs from the current-cycle obligation, which is released after the read date (OD-11) because that obligation is assumed paid; arrears is never assumed paid, so it never releases.

**Interaction with OD-15.** Because the obligation for a past-due occurrence is now carried by `Arrears`, the read date does **not** also count that occurrence as paid and debit the forecast `Balance`: doing both would count the same obligation twice. The due-today occurrence is still counted as paid (it is the current bill), so OD-15's payment-settled accrual add-back and its due-today behaviour are unchanged; only the un-settled **overdue** debit is superseded (§B-04).

### 5. Schema and migration approach

EF migration files are append-only, so the existing accrual migrations remain in sequence and are **not** edited or removed — including their `*.Designer.cs` model snapshots. Dropping the storage is a new migration, and it is the new migration that rewrites `PotDbContextModelSnapshot.cs`; the snapshot is never hand-edited.

Decision: two-step rollout (OD-14):

1. **Stop reading and writing.** Ship the derived read paths and the removal of the command surface, leaving the columns and table in place. Behaviour change only; trivially reversible.
2. **Drop.** A later migration (for example `DropAccountAccrualAndAggregates`) removes `AccountAccrual` and the four columns.

Step 2 is safe from a data-loss perspective because the values are reproducible from source data. Two operational notes:

- PRD-013 gates startup on applied migrations, so a destructive migration is a deploy-time event: replicas still serving during a rolling deploy must no longer depend on the dropped columns, which step 1 guarantees. **Amended 2026-09-27 (user decision) — the rollout is not a rolling deploy.** Production is shut down for a maintenance window, the migration is applied to the stopped system, and the new version starts afterwards, so no replica ever serves pre-drop code against the post-drop schema and the old-replica hazard this note warns about cannot arise. The ordering constraint is unchanged, because step 1 still ships before step 2; it is satisfied by the shutdown instead of by a coordinated rollout.
- `DbContextBase.DisableCascadeDelete` forces `Restrict` on every FK, so the `AccountAccrual → Account` FK is part of the delete ordering. If this feature lands before PRD-022, that PRD's sweep of `AccountAccrual` disappears.

### 6. Maintenance import/export

`AccountsExporter` writes the three aggregates and `ExpensesExporter` writes `Accrued`; both importers already ignore those columns (the assignments are commented out), so neither value round-trips today.

Decision: the derived columns are no longer exported. They would have to be computed at export time to be written at all, they are reproducible from the exported rows, and nothing consumes them on import. `AccountData` / `ExpenseData` (export) and `AccountCsvRow` / `ExpenseCsvRow` with their interfaces (import) lose the corresponding members together, and the narrower header set is verified to round-trip. Only `MetadataV4`'s column list changes: `MetadataV1`–`MetadataV3` document superseded package versions whose exports may exist, so they stay as the historical record, and the accounts importer's commented-out assignments go with the members.

Decision: the maintenance package version stays at **v4**, and the column-set change is made in place.

**Why the in-place change is safe here.** v4 was introduced by PRD-021 on 2026-09-24 and no export has ever been taken from it, so there is no v4 package in the field whose layout another reader could misread. That precondition is load-bearing because the removal is _not_ a trailing-column removal on the expenses side: `ExpenseCsvRow` binds positionally and `Accrued` sits at `[Index(10)]`, with `Note` and `AccountRowId` after it, so removing it re-indexes those two fields. `CsvRowEnumerator` reads the header and then binds by `[Index]`, so an old 13-column `expenses.csv` read by the new 12-index row would move the old `Accrued` into `Note` and the old `Note` into `AccountRowId` rather than failing outright. (The accounts side is genuinely trailing — `TotalExpenseAccrued` and `DailyExpenseAccrual` are the last two indices — so removing them leaves `RowId`–`Reserved` untouched, and `AccountCsvRow` was already asymmetric against its exporter, never declaring `StableExpenseAccrual`.)

**The guard for next time.** The hazard becomes live the first time a v4 export leaves the system. From that point any change to the exported column set — add or remove, anywhere in the row — must bump the package version, per PRD-021's discipline, so superseded exports are rejected rather than misread. The current change is exempt only because the precondition above still holds. `e2e/tests/maintenance/export.test.ts` asserts the exported filename ends `.v4.export` and is unaffected.

### 7. Performance and caching

**Decision: no cache.** Derived values are computed on read. This section records why, and the complete design a future agent would need if measurement ever says otherwise.

`GET /api/accounts` gains one projection query (the account row plus the accrual-relevant expense fields) and a per-account pure calculation.

`GET /api/projections` is unchanged and already the heavier path: it renews and accrues for every account on every day of the window, and it ships today without a cache. That is the scale check for the new work — until the accounts path is measured to be worse than a path that is 365 times larger, a cache would be solving a problem that does not exist.

The projection loop remains the hot path; §1.5's settled P3 (OD-08) keeps it allocation-free apart from the small per-day view records, and the per-expense detail shape is opt-in (§1.4). Repository shape is settled by §1.3: the query projects the input fields per expense rather than loading expense graphs, and for the read paths the input is built once per request.

**Two callers compute accrual they discard.** `AccountsExporter` reads accounts through `IGetAllAccountsService.GetAllAccountsAsync` and, after §6, writes no accrual column; `BudgetReminderService` reads expenses through `IGetExpensesService.GetAllExpensesAsync` and uses only due-date and amount fields. Both therefore pay for the computation this feature adds and throw it away. The cost is small — an on-demand export and a daily worker, neither hot — but the "cheaper than a path 365 times larger" argument above is weakest at exactly these two call sites. They keep the shared reads — **OD-16** settled in favour of accepting the cost rather than adding a second read shape for it — so the two call sites are recorded here as known, deliberate overhead rather than an optimisation left undone.

#### If a cache is ever warranted

A future agent should implement exactly this much and no less. Anything simpler is wrong in a way that will not be visible until a user sees a stale number.

**The cached value has three clocks.** An accrual value changes when the date rolls over, when the rules change, or when the data changes; the key has to carry all three.

| Clock    | Example change                                                | Key component                                                                                          |
| -------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Calendar | the site-local date rolls over                                | `asOfDate` (from `ITimeProvider`, per PRD-018) — a new day is a new key, so nothing needs invalidating |
| Rules    | the accrual arithmetic changes in a deploy                    | `derivationVersion`                                                                                    |
| Data     | an expense is created, edited, deleted, reassigned or toggled | `dataVersion` (per account)                                                                            |

Key: `(accountId, asOfDate, derivationVersion, dataVersion)`.

- **`derivationVersion`** — an assembly/build-derived value (for example `AssemblyInformationalVersion`) is the zero-maintenance choice; a deploy that changes nothing about accruals causes harmless misses. A hand-maintained constant is more precise but fails silently: a missed bump serves values computed by superseded rules, which is worse than having no cache at all.
- **`dataVersion`** — `(maxExpenseEtag, expenseCount)` over the account's expenses, projected in the same accounts query (`account.Expenses.Max(expense => expense.Etag)` and `account.Expenses.Count`). `DbContextBase.OnBeforeSave` re-stamps `Etag` on every added or modified row, so an edit or a creation raises the max, a deletion changes the count (or lowers the max when the deleted row held it), and a reassignment changes both accounts. The account's **own** `Etag` is not usable here: once this PRD removes the accrual command, an expense edit no longer modifies the account row.
- **Cache the view, not `Available`.** `Balance` and `Reserved` are not accrual inputs and are composed where the account response is built (§2), so account-row edits — balance and reserved changes — never need to touch the cache.

**In-process or distributed.** Under this key an in-process `IMemoryCache` is _correct_ on every replica, because the key already contains everything that determines the value: replicas cannot disagree, they only duplicate the work (N× computation, N× memory, each warmed independently). Measured by database load rather than replica CPU, an in-process cache therefore achieves nothing in a horizontally scaled deployment. If the goal is to stop replicas querying the database for the same values, the cache must be distributed (`IDistributedCache`, for example Redis) — which is a new operational dependency for a feature that currently has none. Either way it must be cache-aside with graceful degradation: a miss, a store outage or a deserialisation failure computes the value as today and never fails the request.

**Lifetime and eviction.** Because the key changes whenever the value would, entries are never reused after a change, so time-based expiry is only about reclaiming space. Bound it deliberately: an account accumulates roughly one entry per (day, data version) pair, so size to `accounts × (edits per day + 1)`, or expire entries at the end of the site-local day plus a margin. Apply a size limit so an unusual day cannot exhaust a replica.

**What not to do:**

- A TTL-only cache without the version components briefly serves values computed from superseded data or rules — the exact staleness this PRD removes.
- Eviction call sites in the mutation services instead of a key component is easier to write but is the dirty-flag pattern again, with the same easily-missed paths (reassignment, delete, toggle, renew) that PRD-009 catalogued.
- Caching `Available` instead of the view adds account-row edits as a fourth input for no benefit.

**Multi-tenancy.** `accountId` is globally unique, so no site component is needed while the key is built on account ids; add one only if a future key becomes site-scoped.

Whatever is built should be validated by asserting that cached and freshly computed values agree, and that each data mutation produces a different key.

### 8. Client effects

- `Arrears` and `TotalCommitted` join the account and expense payloads and the client carries them: `src/data/account.ts` gains `totalArrears` / `totalCommitted` and `src/data/expense.ts` gains `arrears`. The past-due portion is then shown on the two tables that already carry the obligations: an `Arrears` column beside `Accrued` in `ExpensesTable.tsx`, and the columns settled below in `AccountsTable.tsx`. The account cards (`AccountCard.tsx`, `AccountMobileCard.tsx`) are deliberately unchanged: their `Daily Need` is a rate, not an obligation. The projection chart reflects arrears through `Available` and gains no field of its own (§1.4, §2, §3.2). No new derived figure (for example a percentage in arrears) is added.
- **The accounts table shows `totalCommitted` as its own column, and its columns are ordered as follows (settled during implementation, 2026-09-27):** `Description`, `Balance`, `Reserved`, `Available`, `Daily Need`, **`Accrued`**, **`Arrears`**, **`Committed`**, then the row actions. The reading order is what the account holds, then the rate, then the commitments left to right — the accrual in progress, the past-due debt, and the headline total defined in §3.2. `Committed` earns a column precisely because it is the aggregate of the two before it: it is the one figure that answers what the account is committed to, and rendering it stops the reader adding the other two up.
- **The obligation column labels are `Accrued`, `Arrears` and `Committed`.** `Arrears` replaces the earlier `Past Due` label, and `Committed` replaces `Outstanding`, the label the field was first given. Both renames are deliberate: `Past Due` read as a status, which it never was, and `Outstanding` — money due and unpaid — fitted the arrears it sums but not the accrual of the cycle in progress, which is not owed yet (§1.1, §3.2). The labels also carry no `Total` prefix, because every figure in the table is already the account's total — the row is the account, so the qualifier would only be noise; the fields keep it (`TotalCommitted`, alongside `TotalExpenseAccrued` and `TotalArrears`). That leaves `Accrued` and `Arrears` matching the per-item columns of `ExpensesTable.tsx` word for word (§3.2), which is what makes the two reads feel like the same measure at two grains; `Committed` is the one that has no per-item counterpart, and it is self-evident sat to the right of the two amounts it sums.
- This column order and these labels are asserted by `tests/features/accounts/components/AccountsTable.test.tsx`, so a later reorder or relabel has to be a deliberate change rather than a silent one.
- **Every column heading on the accounts, expenses and incomes tables carries a hover hint** describing the figure beneath it, so the obligations can be told apart without leaving the page: the accounts hints cover `Accrued`, `Arrears` and `Committed` alongside the established columns, and the expenses and incomes hints cover their own columns. `DataTableColumnHeader` gained an optional `hint` and renders it through a new `components/table/ColumnHeaderHint.tsx`, and each table supplies its own copy so the wording stays beside the columns it describes. The tooltip sets `max-w-sm text-wrap`, because the header primitive's default `text-balance` re-splits a wrapped hint into near-equal lines and so reads as though it wrapped early; the shadcn primitives under `src/components/ui` are not modified. The tests assert the mechanism rather than the copy — hovering a heading exposes exactly one tooltip and sets `aria-describedby` on it — so the wording stays free to change, and `Docs/USER-GUIDE/{Accounts,Expenses,Income}.md` document the behaviour.
- The dashboard no longer shows an "accruals pending" state, because there is nothing to accrue. Numbers are current whenever the accounts query is current, and `expenses → accounts → projections` invalidation already covers edits.
- Quick Actions keeps `RenewExpensesAction` and `RenewIncomesAction`; the combined action is removed rather than reduced (§4). The grid keeps its four desktop columns (`grid-cols-2 lg:grid-cols-4`), so the two remaining tiles sit in the first two and the layout does not shift when further actions are added; the two empty desktop columns are a deliberate trade for that stability, not an oversight.
- No accrual-specific loading or error state is required; the existing accounts query loading/error handling covers the new computation.
- `dailyExpenseAccrual` is dropped from the accounts response and from `src/data/account.ts`, together with the client surface that only existed to carry it: the `totalDailyAccrual` member of `useAccountsSummary.ts` and its computation and store write in `AccountsOverview.tsx` (written but never read), the placeholder entry in `useAccountFilter.ts`, the account factory and the tests that reference it (`tests/data/account.test.ts`, `tests/features/dashboard/stores/useAccountsSummary.test.ts`). No rendered value changes. The calculation still produces the metric — only the accounts response loses the field (§1.1).

## Behaviour Changes

Every user-visible difference this feature introduces, including the defects it fixes. Items are referenced elsewhere in this document as `B-nn`. Two items — **B-04** and **B-06** — are marked _interim only (no net change)_: they record a design that was superseded before implementation and are kept, with their numbers, only so the interim cannot be reintroduced. Unless an item says otherwise the numbers use the §3.1 fixture (whose four rows are the arithmetic authority) and "the chart" / "the accounts read" mean the two `Available` forms defined in §2.

### B-01 — `Available` no longer exceeds `Balance` on a payment day (defect fix)

A bill due on the day being measured is now accrued in full _before_ the schedule is advanced, so the add-back cancels that bill's own obligation instead of crediting the day with a payment the accrual never counted.

| Bill 100 due today, un-renewed — chart | `balance` | `accrued`  | add-back | `Available` | `Balance` |
| -------------------------------------- | --------- | ---------- | -------- | ----------- | --------- |
| Before                                 | 900       | **0.00**   | 100      | **1000.00** | 900       |
| After                                  | 900       | **100.00** | 100      | **900.00**  | 900       |

The `+ expensesPaid` term exists only to cancel the double-count of a row that is both debited from the balance and accrued. Measuring after the advance broke that premise on **every** payment day of the window — a recurring bill due mid-window overshoots exactly as one due on day 0 does — and it also masked a temporary overdraft on the day it existed.

**The everyday case this fixes: a direct debit that has not been processed yet.** A bill is due today, the debit has not come out, and the bank balance still shows the money (1000). The projection must behave as though the payment is already committed, because the window assumes it will be. Before the fix the default `balance` metric read `900` but the `available` metric read `1000` — the two selectable metrics disagreed on a payment day. After the fix both read `900`, which is also what the chart shows once the debit is processed, the bank balance is updated to `900` and the bill is renewed, so the two paths agree. The one way to break that agreement is to update the bank balance to `900` **before** renewing: the window then assumes the payment a second time and reads `800`, which is why balance and renewal are meant to move together.

### B-02 — An un-settled overdue occurrence is measured in full on the read date (as `Arrears`, §3.2)

An occurrence whose due date has passed and that the user has not renewed is measured in full on the read date, rather than showing only the next period's partial ramp. Under §3.2 the full obligation is split: the past-due cycle is carried as `Arrears`, and `Accrued` reports the ramp of the cycle in progress.

| Bill 100 due yesterday, un-renewed — chart | `Accrued` | `Arrears`  | `Available` |
| ------------------------------------------ | --------- | ---------- | ----------- |
| Before                                     | **3.23**  | —          | **996.77**  |
| After                                      | **3.23**  | **100.00** | **896.77**  |

This is what makes the chart show the obligation that is actually outstanding; the old figure understated it by about 97 on a 100 bill. The obligation sits in `Arrears` rather than in `Accrued` so that `Accrued` keeps its bounded current-cycle meaning (§3.2, OD-17).

### B-03 — A non-accruing bill no longer inflates `Available` (defect fix)

The add-back now re-adds only what a row contributed to `accrued`. A row that does not accrue — `AccrualPolicy.None`, or a null `AccrualStart` — contributes nothing, so there is nothing to re-add.

| Bill 100 due today with `AccrualPolicy.None` — chart | `balance` | `accrued` | add-back | `Available` | `Balance` |
| ---------------------------------------------------- | --------- | --------- | -------- | ----------- | --------- |
| Before                                               | 900       | 0.00      | **100**  | **1000.00** | 900       |
| After                                                | 900       | 0.00      | **0**    | **900.00**  | 900       |

`Available > Balance` for `None` rows is a **pre-existing defect** the ordering fix never touched: the bill is paid, so the money has gone, but it was never accrued — and the blanket add-back credited it back anyway. The accounts read is unaffected, because it never applies the assumed payment.

### B-04 — Interim only (no net change): an un-settled overdue bill was to be counted as paid on the read date

The forecast's paid set never includes an un-settled occurrence whose due date has passed: an interim design debited it on the read date, and OD-17 replaced that with the `Arrears` hold.

| Bill 100 due yesterday, un-renewed | Today | Interim — OD-15 | Final — OD-17 (§3.2) |
| ---------------------------------- | ----- | --------------- | -------------------- |
| `ExpensesPaid` on the read date    | **0** | **100**         | **0**                |
| Chart `Balance` from the read date | 1000  | **900**         | 1000                 |
| In the window's expense list / bar | never | read date       | never                |

**Net effect: none.** The interim design debited the overdue row on the read date so that the fold's advance — the model's settlement act — moved money as well as the schedule. OD-17 supersedes that: the occurrence is not counted as paid, and its obligation is carried as `Arrears` and held for the whole window instead (B-10), which keeps the day-1 series continuous without the debit:

| Chart `Available` — 100 bill overdue by a day, un-renewed | day 0      | day 1      |
| --------------------------------------------------------- | ---------- | ---------- |
| Today                                                     | 996.77     | 993.55     |
| Interim — **OD-01 alone** (B-02, no debit)                | 900.00     | 993.55     |
| Interim — OD-15 (with the debit)                          | 900.00     | **893.55** |
| Final — OD-17 (arrears held)                              | **896.77** | **893.55** |

The debit lands on the read date rather than on the occurrence's historical due date because the read date is the earliest day the model measures; the pre-start days are simulated, so a window that starts later still carries the debit forward.

### B-05 — The accrual columns stop being stale and agree with the chart

`TotalExpenseAccrued`, `StableExpenseAccrual` and per-expense `Accrued` are computed on read for today, and the chart's `accrued` comes from the same calculation.

| Account with one 100 bill due today, un-renewed | Accounts "Total Accrued"                                                   | Expenses "Accrued" | Chart `accrued`                       |
| ----------------------------------------------- | -------------------------------------------------------------------------- | ------------------ | ------------------------------------- |
| Before                                          | last manual accrual's value — stale from the next day boundary or any edit | same staleness     | **0.00** (measured after the advance) |
| After                                           | **100.00**                                                                 | **100.00**         | **100.00**                            |

No existing column is removed, and no rendered value changes except through the corrections above; what changes is that these figures are now current and consistent, with the arrears figures sitting alongside them (§3.2). This is the "one derivation" goal the feature exists for.

### B-06 — Interim only (no net change): `dailyAccrual` for an un-settled overdue row was to become `0`

For a bill 100 due yesterday and un-renewed, the read-date `dailyAccrual` starts and finishes at ≈`3.23`, but one interim design passed through `0`:

| Bill 100 due yesterday, un-renewed — chart   | `dailyAccrual` | Why                                                                                                                                                                                   |
| -------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Today                                        | ≈**3.23**      | the loop measures after its own catch-up, so `Accrued` is the ramp toward the next due date and `DailyBalance` is `(100 − 3.23) / 30 ≈ 3.23`                                          |
| Interim — OD-15 (measure before the advance) | **0.00**       | measuring the persisted, un-settled occurrence accrues it in full (`Accrued = 100`), so `Amount − Accrued` is `0` and no remaining balance is left to spread — **superseded by §3.2** |
| Final — OD-17 (arrears, §3.2)                | ≈**3.23**      | the full obligation is carried as `Arrears`, so `Accrued` is the cycle in progress again and the rate returns to ≈`3.23`                                                              |

**Net effect: none.** `Arrears` restores the read-date rate the interim computation removed, so the overdue row and the due-today row both report ≈`3.23` on the read date — reached by different expressions, `DailyBalance` (`(100 − 3.23) / 30`) on the overdue row and `Amount / daysToNextDue` (`100 / 31`) on the due-today row, so they agree to two decimals for this fixture without being the same expression (§3.1 note 7). The item is retained rather than deleted so an implementer cannot reintroduce the `0`, which a literal reading of "the overdue occurrence is accrued in full" would produce.

### B-08 — The accounts response no longer carries `dailyExpenseAccrual`

| `GET /api/accounts` | Fields                                                                          |
| ------------------- | ------------------------------------------------------------------------------- |
| Before              | `… totalExpenseAccrued, dailyExpenseAccrual, stableExpenseAccrual, available …` |
| After               | `… totalExpenseAccrued, stableExpenseAccrual, available …`                      |

A response-shape change with no rendered effect: the field had no reader (it was summed into `totalDailyAccrual`, which nothing rendered). The calculation still produces the metric, because the projection response consumes it.

### B-09 — The maintenance export no longer carries the accrual columns

| File           | Before                                                                                                    | After                                 |
| -------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `accounts.csv` | RowId, Description, Balance, Reserved, **TotalExpenseAccrued, DailyExpenseAccrual, StableExpenseAccrual** | RowId, Description, Balance, Reserved |
| `expenses.csv` | … Amount, **Accrued**, Note, AccountRowId                                                                 | … Amount, Note, AccountRowId          |

The values would have to be computed at export time to be written at all, they are reproducible from the exported rows, and no importer consumed them. The package stays at **v4** because no v4 export has ever been taken (§6), and the narrower header set still round-trips.

### B-10 — Past-due cycles are counted as `Arrears`

An item the schedule has fallen behind on now carries an `Arrears` amount — one `Amount` per past-due, un-settled occurrence — alongside the accrual of the cycle in progress; the accounts read and the expenses list carry it, and the projection reflects it through `Available`.

| $70 weekly bill ($10/day), 2 cycles missed, 3 days into the 3rd — read date | `Accrued` | `Arrears`  | `TotalCommitted` | `Available` |
| --------------------------------------------------------------------------- | --------- | ---------- | ---------------- | ----------- |
| Before (one obligation per item)                                            | 30.00     | —          | 30.00            | 970.00      |
| After                                                                       | 30.00     | **140.00** | **170.00**       | **830.00**  |

The accrual rule is unchanged; what is new is that the obligation for the cycles already behind is counted at all. `Arrears` is held for the whole forecast window (§3.2), so it reduces `Available` on every day of the chart rather than only the read date, and it is not debited from the forecast `Balance`.

### B-11 — The accounts table gains a `Committed` column and renames `Past Due`

| `AccountsTable.tsx` | Before                      | After                                             |
| ------------------- | --------------------------- | ------------------------------------------------- |
| Obligation columns  | `Total Accrued`, `Past Due` | `Accrued`, `Arrears`, **`Committed`**             |
| `Past Due` label    | A status-sounding name      | `Arrears` — the same figure, named for what it is |
| `Outstanding` label | A settled-debt word         | `Committed` — the accrued cycles plus the arrears |

The three obligation columns now sit together at the right of the table, in the order accrual in progress → past-due debt → total, so the headline figure §3.2 defines is rendered rather than left for the reader to add up. Before the change the two obligation columns sat mid-table and the total was not shown at all. Settled as a requirement in §8, which fixes the full column order, and asserted by `tests/features/accounts/components/AccountsTable.test.tsx`.

### Not changed

- `NextDue` and renewal semantics. The overdue/due-today/ended badges, the reminder windows and the bulk renew breakdown are untouched, because nothing here moves the persisted cursor.
- The chart's `Available` **add-back** itself — still the documented payment-settled accrual add-back (OD-15). The accounts read's formula does change: it becomes `Balance − Reserved − TotalExpenseAccrued − TotalArrears` (§3.2).
- Accrual policy modes (`Automatic` / `None`) and the accrual boundary conventions (PRD-003, PRD-009). `None` still means "scheduled and paid, but not accrued" for `Accrued`; `Arrears` is schedule-derived and independent of the policy (§3.2).
- Write endpoints: every create/update/delete/toggle/renew payload is unchanged. On the read side only two things change: B-08 (the dropped `dailyExpenseAccrual`) and the arrears additions (§3.2, OD-17).

### Arrears decision

**OD-17 — how a past-due occurrence is represented, and for how long.** One `Amount` per missed cycle, carried as `Arrears` (not folded into `Accrued`), held for the whole forecast window, and **not** debited from the forecast `Balance`. **Settled:** the arrears model in §3.2.

- `Accrued` keeps its bounded current-cycle meaning, so the rate metrics and the `Amount − Accrued` arithmetic stay valid; `Arrears` is the named past-due component; `TotalCommitted = Accrued + Arrears` is the headline. `Available` subtracts both.
- Arrears is held for the whole window because it is pre-existing debt the window never assumes is repaid — it is not released like the current-cycle obligation (OD-11) and is not debited like a payment (OD-15 option (a)).
- The due-today boundary is explicit: an occurrence due on the read date is the current bill, accrued in full and assumed paid, and is **not** arrears.
- This supersedes OD-12, OD-01's full-`Amount` measurement for occurrences already past due (they are now `Arrears` while the cycle in progress ramps), and, for rows carried in arrears, OD-15 option (a)'s overdue debit.

## Design Notes (Rationale and Rejected Alternatives)

**Why not "accrue automatically after each expense change" (the original idea).** It addresses only the event clock. The calendar clock still marks every account stale each day, so the user would still face a pending state daily — the exact irritation the idea was meant to remove. It also reintroduces the write amplification and etag churn of §Problem 1 on the mutation path, re-runs a whole-account recalculation per edit (undoing the batching the manual action was originally added for), and leaves the two derivations of `Available` in place.

**Why not "accrue on login".** Idempotency is free (`RequiresAccrualUpdate` makes a second login in a day a read-only no-op), but it couples a write to the authentication path, still writes and re-stamps etags once per user per day, and does not help a session left open across midnight.

**Why not a scheduled worker.** It covers users who never open the app, but adds a new scheduling surface with the same failure classes already tracked for the existing workers (per-replica execution, missed windows on restart, catch-up), for a value that is idempotent and cheap to compute on read. It is the most machinery for the least additional correctness.

**Why not "accrue if stale inside a GET".** A write inside a read is impure: it mutates `Etag`s, surprises caching and concurrency, and fails against read replicas. If materialisation is ever required again, a version-keyed cache (§7) is the shape that does not have these properties.

**Why the schedule cursor is _not_ derived.** An earlier draft proposed deriving `NextDue` too, treating it as a recurrence anchor and computing the current due date on read. That would erase the overdue concept: renewal is currently the only record that an occurrence has been acknowledged, and overdue drives badges (`badgeStyles`, `tableRowUtils`), `getDaysDue` status derivation, dashboard overview windows, the bulk renew breakdown (`Overdue` vs `Future`) and `BudgetReminderService`. Deriving the cursor would have required a persisted acknowledgement fact and migration seeding to preserve behaviour — a much larger change, and one that belongs with the settlement track (PRD-024) rather than here.

**Why an immutable record input rather than a mutable model, and rather than the entities.** The rule this feature is built on is that a derived value must never be persisted. Expressed against entities, that rule survives only because the projection path happens to run no-tracking; a single `WithTracking()` scope opened elsewhere in the same request would turn an accrual mutation into an `Etag`-stamping `Modified` row on the next save. A mutable DTO removes the entity hazard but keeps the mutation idiom, leaves "what changed this iteration" implicit, and makes a shared snapshot unsafe. Immutable records make the rule structural, and `with`-expression variation is exactly what a later date-varied or what-if analysis (PRD-024) would want.

**Why one shared input type rather than a data-layer DTO plus an app mapping (OD-09).** The field set _is_ the accrual-relevant fact set for an expense, and every consumer needs exactly it, so a single shared record gives one shape, no mapper and no drift, with no dependency inversion. The nearest precedent (`AccountWithLinkedCounts`) bundles an entity with counts and exists for one repository's needs; this model is narrower and is not repository-specific, which is why it does not need to live beside a repository.

**Why the detailed view is a separate entry point (OD-10).** The projection loop runs the calculation for every account on every day of the window. A per-expense collection materialised on each of those calls would allocate for data that nothing reads, so the aggregate shape is the default and the detail shape is explicit.

**Why per-expense accrued is not narrowed to the expenses list.** It is already on the canonical expense payload, which serves the table, the mobile card, the dashboard overview and the account filter's derived list; narrowing it would add a second contract, or a flag, for a value those surfaces may legitimately render, and would save nothing server-side because the per-row figure is a by-product of the calculation the list requires anyway. The write responses stay without it because they have no reader, and the projection detail stays without it because producing per-item accrued for every day of the window would multiply the detail shape's cost by the window length rather than compute it once for the date on screen.

**Why renewal is also a pure calculation under P3 (OD-08).** Renewal and accrual read the same schedule through different lenses: renewal advances it, accrual measures it. Expressing renewal as a fold over an immutable cursor removes the ordering hazard in the projection loop (accruing against pre-renewal dates), makes the renewal rules unit-testable without entities, and costs a two-date value type per step rather than an allocation. Persistence is unaffected: the renewal command still writes the computed cursor back to the entity, because a schedule advance is a fact, not a derived value. The expense fold reuses `ExpenseAccrualInput`, whose field set already covers renewal, while an income has no accrual state and so folds a narrow `IncomeScheduleInput`; the entity-facing calculators delegate to the folds, so the renewal rules live in one place rather than being duplicated across the command and projection paths.

**Why the projection must measure before it advances.** `Source/Server/IMPLEMENTATION.md` states that on the due date `Accrued` is the full `Amount`, and `MapToDateBalanceAvailable` relies on that when it adds `ExpensesPaid` back. An implementation that advances the schedule first — as today's loop does — measures the next period instead, which is what broke the add-back and produced the payment-day `Available` overshoot. Applying the rule at the start of **every** day — not to the read date alone — makes the documented behaviour structural rather than a comment the ordering silently contradicts; measuring at the start of the day is therefore a restoration of documented behaviour in the projection path, not a new convention, and it is what stops a recurring bill due mid-window from overshooting the same way a day-0 bill does (OD-15).

**Why the un-acknowledged obligation is released after the read date (OD-11).** The window assumes income is received and expenses are paid on time, so a due-today row's day-0 balance already has the payment taken out of it — that is where row 3's 900 comes from. Row 4's 900 has a different origin: an un-settled overdue row is not due on the read date, so it is not in `expensesPaid`, the balance keeps its 1000, and the figure is the accrual alone. That asymmetry — the same "released" treatment applied to a row whose payment the window never deducted — is what **OD-15** exists to resolve. Holding the obligation for the rest of the window would then subtract the same amount a second time against that balance, showing an account 100 worse off for a payment the forecast itself assumed was made. Releasing it keeps the projection internally consistent, while the read date still separates settled from un-settled (900 against 1000), which is the whole point of measuring the persisted cursor (OD-01). The two views are not in conflict: the account card reads the user's own maintained balance and holds the obligation until renewal, and the chart assumes the payment and moves on. **Superseded for past-due rows by OD-17 (§3.2):** the un-settled overdue obligation is now held as `Arrears` for the whole window rather than resolved by a read-date debit, so the row-4 `900` above becomes `896.77` and no day-1 asymmetry arises.

**Why the past-due obligation is now counted per skipped cycle (OD-17, superseding OD-12).** POT still forecasts forward on the basis that income is received and expenses are paid on time _from today onward_, but it also reflects how far behind the account already is, because that debt has a real effect on available funds. The count is derivable from the schedule — frequency plus the persisted `NextDue` — so it needs no payment history, and the current `Amount` is used for each past-due occurrence. Keeping the past-due amount as a separately-named `Arrears` (rather than folding it into `Accrued`) is what stops the change altering what `Accrued` means; PRD-024 remains a history record that cannot be read by this calculation.

**Why the projection engine is the reference.** It already recomputes renewal and accrual per day, per account, without persisting, and is validated by `Pot.App.Tests/Features/Projections/ProjectionsServiceFixture.cs`. This feature generalises that proven path rather than inventing a new one; the projection fixtures remain the guard that the shared engine changes nothing beyond the settlement basis decided in §3.1.

## Non-Goals

- Any settlement, actuals, or occurrence-history store. See [PRD-024 — Settlement Ledger](PRD-024-settlement-ledger.md), which is a history record and must not be read by this calculation. POT is a forecasting tool rather than a full financial-tracking application: it still projects available funds on the basis that income is received and expenses are paid on time _from today onward_, and it does not record what was actually paid. It does now reflect **how far behind** the schedule already is, as `Arrears` (§3.2) — a schedule-derived figure, not a payment record.
- Changing what "available" means, or the formulas that produce it.
- Changing accrual policy modes (PRD-003) or the accrual boundary conventions (PRD-009) beyond moving where and when they are applied.
